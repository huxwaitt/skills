# Google Cloud: access, identity, roles, governance and commercial model (as of 2026-11-14)

## 1. Getting access
- **Vertex AI is now part of Gemini Enterprise Agent Platform.** Google's release notes dated 2026-04-22 list the renames Vertex AI to Agent Platform, Vertex AI Studio to Agent Studio, Vertex AI Search to Agent Search, Vertex AI RAG Engine to RAG Engine, and Vertex AI Agent Engine to Agent Runtime. They also say "Agent Builder is now part of Gemini Enterprise Agent Platform." IAM role IDs keep the `roles/aiplatform.*` and `roles/discoveryengine.*` prefixes. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Google Cloud docs moved to docs.cloud.google.com.** `https://cloud.google.com/docs`, `https://cloud.google.com/vertex-ai/docs` and `https://cloud.google.com/iam/docs` return 301 redirects to `https://docs.cloud.google.com/...`. The new Agent Platform docs root is `https://docs.cloud.google.com/gemini-enterprise-agent-platform`, organised into Build, Scale, Govern and Optimize. Source: https://docs.cloud.google.com/docs ; https://docs.cloud.google.com/gemini-enterprise-agent-platform
- **Resource hierarchy.** The hierarchy runs Organization (root), then optional nestable Folders, then Projects, then service resources. Every resource except the root has exactly one parent. Allow, deny and organization policies set at the organization or a folder are inherited by all descendants. Source: https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy
- **An Organization resource requires Google Workspace or Cloud Identity.** Each Workspace or Cloud Identity account links to exactly one organization, which is provisioned automatically when a user in that account creates a project. The initial allow policy grants Project Creator and Billing Account Creator to the whole domain. Source: https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy
- **The Workspace or Cloud Identity super admin bootstraps IAM.** The super admin verifies the domain and assigns the Google Cloud Organization Administrator role (`roles/resourcemanager.organizationAdmin`) to the people who then administer IAM across the hierarchy. Source: https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy
- **Project ID vs project number.** The project ID is chosen at creation and used in most requests. The project number is generated automatically, is read-only, and is what service agent emails and federation principal identifiers use. Source: https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy ; https://docs.cloud.google.com/iam/docs/workload-identity-federation
- **Google Cloud Setup offers three foundation tiers.** "Proof of concept" covers organization, billing and hierarchy. "Production" adds logging, monitoring and Security Command Center. "Advanced production" adds networking and Cloud KMS with Autokey. Source: https://docs.cloud.google.com/docs/enterprise/setup-checklist
- **Billing account roles decide who can attach projects to billing.** The roles are `roles/billing.admin` (Billing Account Administrator), `roles/billing.user` (Billing Account User, links projects), `roles/billing.viewer`, `roles/billing.projectManager` (Project Billing Manager) and `roles/billing.creator` (Billing Account Creator, granted at the organization). Linking a project needs `roles/billing.user` on the billing account plus `roles/billing.projectManager` or Owner on the project. Source: https://docs.cloud.google.com/billing/docs/how-to/billing-access
- **Enterprise procurement can go through Google Cloud Marketplace private offers.** Accepting a private offer needs `roles/billing.admin`, or `roles/billing.user` plus `roles/consumerprocurement.orderAdmin`, on the Cloud Billing account named in the offer. An offer can be accepted only once. Source: https://docs.cloud.google.com/marketplace/docs/offers/accepting-private-offer
- **Partner models in Model Garden (for example Anthropic Claude) need a procurement entitlement.** An admin with Consumer Procurement Entitlement Manager (`roles/consumerprocurement.entitlementManager`) enables the model. The Cloud Commerce Consumer Procurement API (`cloudcommerceconsumerprocurement.googleapis.com`) must be allowed if service usage is restricted. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-partner-models
- **Express mode is a trial path that does not require a full project setup.** Agent Platform express mode is open to @gmail.com Google Accounts. It has a 90-day limit, offers only basic generative AI services, and authenticates with an API key against the global `aiplatform.googleapis.com` endpoint, whose paths have no project or location segment. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/start/express-mode/overview
- **What to ask the client for on day one.** Ask for the following:
  - an org-domain or federated user identity;
  - a project (with its ID and number) under the right folder, linked to a billing account;
  - the APIs enabled, which needs `roles/serviceusage.serviceUsageAdmin` (example API: `aiplatform.googleapis.com`);
  - `roles/aiplatform.user` on the project;
  - `roles/iam.serviceAccountUser` on the runtime service account;
  - the region and endpoint policy (regional, `us`/`eu` multi-region, or global);
  - the VPC-SC perimeter membership;
  - any `vertexai.allowedModels` restrictions;
  - partner-model enablement, if needed.

  This list is synthesised from Google's setup and access-control pages. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime/setup ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/control-model-access

## 2. Identity and authentication
- **Human SSO through Cloud Identity or Workspace SAML.** Cloud Identity and Google Workspace support SAML 2.0 SSO, with Google as the service provider. Options are SAML profiles (multiple IdPs) or the legacy single-IdP profile. IdP-initiated sign-on is not supported. Super admins can bypass SSO, so their MFA must be set up in Google directly. Source: https://docs.cloud.google.com/architecture/identity/single-sign-on
- **Workforce Identity Federation gives sync-less SSO.** Users from any OIDC or SAML 2.0 IdP (Entra ID, AD FS, Okta) sign in without being copied into Cloud Identity. Workforce pools are configured at the organization level. Principals look like `principal://iam.googleapis.com/locations/global/workforcePools/POOL_ID/subject/SUBJECT`. Token exchange defaults to 1,000 requests per minute per organization. Source: https://docs.cloud.google.com/iam/docs/workforce-identity-federation
- **SCIM for Workforce Identity Federation was announced at Next '26.** Google's IAM blog of 2026-05-06 lists it without stating a status. Source: https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/
- **Google Cloud 2SV/MFA requirement.** 2-step verification is enforced for sign-in to the Google Cloud console and the Firebase console, not for the gcloud CLI or for data-plane traffic. Enforcement dates:
  - personal accounts: on or after 2025-05-12;
  - non-SSO Cloud Identity organizations created before 2026-08-03: on or after 2026-10-20;
  - organizations created on or after 2026-08-03: 30 days after creation;
  - federated/SSO users: "To be announced".

  Source: https://docs.cloud.google.com/docs/authentication/mfa-requirement
- **Google Cloud service account types.** There are three types. User-managed service accounts are created by you. Default service accounts are created when some services are enabled, for example `PROJECT_NUMBER-compute@developer.gserviceaccount.com`. Service agents are Google-managed. Attaching a service account to a resource needs `roles/iam.serviceAccountUser`; managing it needs `roles/iam.serviceAccountAdmin`. Source: https://docs.cloud.google.com/iam/docs/service-account-overview
- **Service account impersonation.** A principal with `iam.serviceAccounts.getAccessToken` gets short-lived tokens for a service account. That permission is in Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`). In gcloud, use `--impersonate-service-account` or the `impersonate-service-account` property. Audit logs typically record both the caller and the service account. Source: https://docs.cloud.google.com/iam/docs/service-account-impersonation
- **Access token lifetime.** Service account access tokens default to a maximum of 1 hour (3,600 s). They can be extended to 12 hours (43,200 s) by listing the service account in `constraints/iam.allowServiceAccountCredentialLifetimeExtension`. ID tokens last 1 hour. Source: https://docs.cloud.google.com/iam/docs/create-short-lived-credentials-direct
- **Secure-by-default organizations block service account keys.** Organizations created on or after 2024-05-03 enforce these constraints by default:
  - `constraints/iam.managed.disableServiceAccountKeyCreation`
  - `constraints/iam.disableServiceAccountKeyUpload`
  - `constraints/iam.automaticIamGrantsForDefaultServiceAccounts`, which stops default service accounts getting Editor
  - `constraints/iam.allowedPolicyMemberDomains`, which is domain-restricted sharing
  - `constraints/storage.uniformBucketLevelAccess`

  Plan for keyless authentication. Source: https://docs.cloud.google.com/resource-manager/docs/secure-by-default-organizations
- **Workload Identity Federation (keyless) basics.** It supports AWS, Azure/Entra ID, GitHub, GitLab, Terraform, Kubernetes, Okta, X.509, AD FS, and any OIDC or SAML 2.0 IdP. The pieces are:
  - workload identity pools, with one pool per environment recommended;
  - providers;
  - Security Token Service token exchange per RFC 8693;
  - CEL attribute mappings (`google.subject` is required, max 127 characters; up to 50 custom attributes);
  - attribute conditions.

  Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation
- **Federated principal identifiers.** A single subject is `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL_ID/subject/SUBJECT`. Groups and attributes use `principalSet://.../group/GROUP_ID` and `principalSet://.../attribute.NAME/VALUE`. Use the project number, not the project ID. Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation
- **Two federation access methods.** Direct resource access grants roles straight to the `principal://` or `principalSet://` identifier; Google recommends it, though some APIs have limitations. Service account impersonation instead grants the federated principal `roles/iam.workloadIdentityUser` on a service account. Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation
- **GitHub Actions federation.** Setup details:
  - Issuer: `https://token.actions.githubusercontent.com/`. The minimum mapping is `google.subject=assertion.sub`.
  - An attribute condition is required because GitHub shares one issuer across all orgs, for example `assertion.repository_owner=='ORG'`. Google recommends the numeric `repository_id` and `repository_owner_id` claims.
  - Creating pools needs `roles/iam.workloadIdentityPoolAdmin`.
  - The job needs `permissions: id-token: write`.

  Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines
- **The `google-github-actions/auth` action is at v3.** It lists three options in order of preference: direct Workload Identity Federation, federation through a service account, and service account key JSON. Direct federation tokens last at most 10 minutes. Not all resources accept `principalSet`. Minting OAuth access or ID tokens requires the service-account path. Source: https://github.com/google-github-actions/auth
- **Federation from AWS.** Create the provider with `create-aws` and the 12-digit account ID. Suggested mapping is `google.subject=assertion.arn` plus `attribute.aws_role=assertion.arn.extract('assumed-role/{role_name}/')`. Recommended condition is `assertion.arn.startsWith('arn:aws:sts::AWS_ACCOUNT_ID:assumed-role/')`. Add `--enable-imdsv2` to `gcloud iam workload-identity-pools create-cred-config ... --aws` for IMDSv2 instances. Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-clouds
- **Federation from Azure.** Create an OIDC provider with issuer `https://sts.windows.net/TENANT_ID` and allowed audience set to the Entra app's Application ID URI (for example `api://my-app`). Map `google.subject=assertion.sub`; for a managed identity the `sub` is its Object ID. Generate the credential file with `create-cred-config ... --azure --app-id-uri`. Source: https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-clouds
- **Google Cloud Agent Identity is an identity type made for AI agents.** Each agent gets a SPIFFE-based identity, `spiffe://TRUST_DOMAIN/resources/SERVICE/RESOURCE_PATH`, that is used in IAM as `principal://TRUST_DOMAIN/...`. The trust domain is `agents.global.org-ORGANIZATION_ID.system.id.goog`, or `agents.global.proj-PROJECT_NUMBER.system.id.goog` when there is no organization. An X.509 certificate is auto-provisioned, valid 24 hours, and renewed automatically. Supported on Agent Runtime, Gemini Enterprise, Cloud Run and GKE. Source: https://docs.cloud.google.com/iam/docs/agent-identity-overview
- **Agent Identity status.** Release notes say Agent Identity reached GA on 2026-04-22 and the Agent Identity API (`agentidentity.googleapis.com`) entered Preview on 2026-06-18. Google's IAM blog of 2026-05-06 lists:
  - GA: Agent Identity for Agent Runtime, and IAM Allow and Deny policies for Agent Identity.
  - Preview: Agent Identity for Agent Platform, Agent Identity Auth Manager, Principal Access Boundary for Agent Identity, and VPC-SC ingress and egress rules for Agent Identity.

  Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes ; https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/
- **Agent Identity principal formats for Agent Runtime.** Examples:
  - one agent: `principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/ENGINE_ID`
  - all agents in a project: `principalSet://agents.global.org-ORG_ID.system.id.goog/attribute.platformContainer/aiplatform/projects/PROJECT_NUMBER`
  - all agents in an org: `principalSet://agents.global.org-ORG_ID.system.id.goog/*`

  Source: https://docs.cloud.google.com/iam/docs/auth-agent-own-identity
- **Agent Identity tokens are certificate-bound by default.** A Google-managed Context-Aware Access policy binds tokens to the agent's certificate, enforcing DPoP and mTLS. ID tokens carry a `cnf` (`x5t#S256`) claim. To call a plain `*.run.app` URL, opt out per request with `bind_id_token=False` (`google-auth` 2.61.0 on GKE, 2.62.0 on Cloud Run). `GOOGLE_API_ENABLE_RUNTIME_BOUND_TOKEN=false` turns binding off across the runtime and is discouraged. Source: https://docs.cloud.google.com/iam/docs/auth-agent-own-identity
- **Enabling Agent Identity on an Agent Runtime agent.** Set `identity_type` to `AGENT_IDENTITY` in one of three ways: `types.IdentityType.AGENT_IDENTITY` in the Python SDK, `agents-cli deploy --agent-identity`, or the ADK `.agent_engine_config.json`. Instances without the flag keep using service accounts; `effectiveIdentity` shows which identity is in use. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/agent-identity
- **Agent Identity Auth Manager brokers credentials for agents.** It is a credential vault and broker for API keys, OAuth client credentials and delegated end-user OAuth tokens. It handles user sign-in, consent and revocation, and attributes end-user access events to the agent's SPIFFE ID. It was Preview per the 2026-05-06 IAM blog. Source: https://docs.cloud.google.com/iam/docs/agent-identity-overview ; https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/

## 3. Roles and permissions
- **Google Cloud IAM model.** You grant roles, which bundle permissions, to principals on resources through allow policies. Effective access is the union of a resource's policy and its ancestors' policies. On top of that:
  - deny policies block permissions even when a role grants them;
  - Principal Access Boundary policies limit which resources a principal is eligible to access;
  - IAM Conditions add attribute-based logic.

  Role types are basic (Owner/Editor/Viewer, not recommended in production), predefined and custom. Source: https://docs.cloud.google.com/iam/docs/overview
- **Core Agent Platform roles.** These keep the `roles/aiplatform.*` IDs:
  - `roles/aiplatform.admin` (full access)
  - `roles/aiplatform.editor`
  - `roles/aiplatform.user`, titled "Agent Platform User", use access to most resources; includes `aiplatform.endpoints.predict`
  - `roles/aiplatform.viewer`

  Source: https://docs.cloud.google.com/vertex-ai/docs/general/access-control ; https://docs.cloud.google.com/iam/docs/roles-permissions/aiplatform
- **Agent-specific Agent Platform roles, all Beta.** `roles/aiplatform.agentsAdmin` covers agents, their memories and access control policies. `roles/aiplatform.agentsCreator` creates and discovers agents and auth providers. `roles/aiplatform.agentsUser` views agents and manages their tasks. `roles/aiplatform.agentsViewer` is read-only. Source: https://docs.cloud.google.com/vertex-ai/docs/general/access-control
- **Memory Bank and Sessions roles.** Memory Bank: `roles/aiplatform.memoryEditor`, `roles/aiplatform.memoryUser`, `roles/aiplatform.memoryViewer`. Sessions: `roles/aiplatform.sessionEditor`, `roles/aiplatform.sessionUser`, `roles/aiplatform.sessionViewer`. Source: https://docs.cloud.google.com/vertex-ai/docs/general/access-control
- **Express and Provisioned Throughput roles.** `roles/aiplatform.expressUser` and `roles/aiplatform.expressAdmin` (Beta) cover express mode. `roles/aiplatform.provisionedThroughputAdmin` (Beta) creates, views, updates and cancels Provisioned Throughput orders. Source: https://docs.cloud.google.com/vertex-ai/docs/general/access-control ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/provisioned-throughput/purchase-provisioned-throughput
- **Roles to deploy to Agent Runtime.** The deployer needs:
  - `roles/aiplatform.user` on the project;
  - `roles/storage.admin` on the staging bucket, only when deploying from an agent object (source-file deploys need no bucket);
  - `roles/iam.serviceAccountUser` on a custom runtime service account, if one is used.

  Enabling APIs needs `roles/serviceusage.serviceUsageAdmin`. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime/setup
- **Agent Runtime's default identity is the Reasoning Engine service agent.** It is `service-PROJECT_NUMBER@gcp-sa-aiplatform-re.iam.gserviceaccount.com` with `roles/aiplatform.reasoningEngineServiceAgent`, which carries the default permissions deployed agents need. Add roles to it if the agent needs more. Reading Secret Manager secrets needs `roles/secretmanager.secretAccessor`. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime/setup ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access
- **A custom service account for Agent Runtime needs extra setup.** It "likely needs" `roles/aiplatform.user` plus whatever the agent code requires. For a service account in another project:
  - `iam.disableCrossProjectServiceAccountUsage` must not be enforced in the account's project;
  - the Agent Platform Service Agent needs `roles/iam.serviceAccountTokenCreator` in that project.

  Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/runtime/setup
- **Least privilege for an agent identity.** Agent identities get `roles/aiplatform.agentDefaultAccess` and `roles/aiplatform.agentContextEditor` by default. Recommended extras are `roles/serviceusage.serviceUsageConsumer`, `roles/browser`, `roles/secretmanager.secretAccessor` and `roles/storage.objectViewer`. Agent-to-agent calls need `roles/agentregistry.viewer`, plus `roles/aiplatform.user` on the target reasoning engine. The docs advise against project-level `roles/aiplatform.user` for agent identities. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/agent-identity ; https://docs.cloud.google.com/iam/docs/auth-agent-own-identity
- **Agent identity bindings are lifecycle-sensitive.** Deleting an agent leaves its IAM bindings in place, so remove them manually. A redeployed agent with a new resource ID is a new principal and needs fresh grants. Agent identities cannot hold legacy Cloud Storage bucket roles such as `storage.legacyBucketReader`. Source: https://docs.cloud.google.com/iam/docs/agent-identity-overview
- **Agent Platform service agents.** The main ones, each with its email and role:
  - Agent Platform (AI Platform) Service Agent: `service-PROJECT_NUMBER@gcp-sa-aiplatform.iam.gserviceaccount.com`, role `roles/aiplatform.serviceAgent`
  - RAG Data Service Agent: `service-PROJECT_NUMBER@gcp-sa-vertex-rag.iam.gserviceaccount.com`, role `roles/aiplatform.ragServiceAgent`
  - Custom Code Service Agent: `@gcp-sa-aiplatform-cc`, role `roles/aiplatform.customCodeServiceAgent`
  - Reasoning Engine: `@gcp-sa-aiplatform-re`, role `roles/aiplatform.reasoningEngineServiceAgent`
  - Fine Tuning: `@gcp-sa-aiplatform-ft`
  - Rapid Eval: `@gcp-sa-vertex-eval`
  - Memory Bank: `@gcp-sa-vertex-memory`

  Source: https://docs.cloud.google.com/iam/docs/service-agents ; https://docs.cloud.google.com/vertex-ai/docs/general/access-control
- **Service agent handling.** Agent Platform service agents are created on first use, or explicitly with `gcloud beta services identity create`. To use data in another project (BigQuery, Cloud Storage), grant the service agent roles there; in the console, tick "Include Google-provided role grants". Don't remove default service agent roles, and never grant service agent roles to humans. Source: https://docs.cloud.google.com/vertex-ai/docs/general/access-control
- **Other agent-relevant service agents.** Each with its email and role:
  - Discovery Engine (Agent Search / Gemini Enterprise): `service-PROJECT_NUMBER@gcp-sa-discoveryengine.iam.gserviceaccount.com`, role `roles/discoveryengine.serviceAgent`
  - Cloud Run: `service-PROJECT_NUMBER@serverless-robot-prod.iam.gserviceaccount.com`, role `roles/run.serviceAgent`
  - Apigee: `service-PROJECT_NUMBER@gcp-sa-apigee.iam.gserviceaccount.com`, role `roles/apigee.serviceAgent`
  - BigQuery Connection: `@gcp-sa-bigqueryconnection`, role `roles/bigqueryconnection.serviceAgent`
  - Agent Gateway: `@gcp-sa-agentgateway`, role `roles/agentgateway.serviceAgent`

  Source: https://docs.cloud.google.com/iam/docs/service-agents
- **Agent Search (formerly Vertex AI Search) roles.** These keep the Discovery Engine names: `roles/discoveryengine.admin`, `roles/discoveryengine.editor`, `roles/discoveryengine.user` and `roles/discoveryengine.viewer`. `roles/monitoring.viewer` may also be needed to see app monitoring. Source: https://docs.cloud.google.com/generative-ai-app-builder/docs/access-control
- **BigQuery roles for agent runtime identities.** Typical least-privilege pairing is `roles/bigquery.jobUser` (run queries; project, folder or org level only) plus `roles/bigquery.dataViewer` on specific datasets. Broader roles: `roles/bigquery.user`, `roles/bigquery.dataEditor`, `roles/bigquery.dataOwner`, `roles/bigquery.admin`. Related: `roles/bigquery.readSessionUser` (Storage Read API) and `roles/bigquery.connectionUser`. Source: https://docs.cloud.google.com/bigquery/docs/access-control
- **Cloud Run roles.** The roles are `roles/run.admin`, `roles/run.developer`, `roles/run.viewer`, `roles/run.invoker`, `roles/run.servicesInvoker`, `roles/run.jobsExecutor` and `roles/run.sourceDeveloper`. Deploying needs `roles/run.developer`, `roles/iam.serviceAccountUser` (`iam.serviceAccounts.actAs`) on the runtime service account, and `roles/artifactregistry.reader`. The runtime defaults to the Compute Engine default service account; Google recommends a dedicated user-managed one. Source: https://docs.cloud.google.com/run/docs/reference/iam/roles
- **Apigee roles.** The roles are `roles/apigee.admin` (Org Admin, the only role that can create or delete organizations), `roles/apigee.apiAdminV2`, `roles/apigee.developerAdmin`, `roles/apigee.environmentAdmin`, `roles/apigee.analyticsViewer` and `roles/apigee.readOnlyAdmin`. Source: https://docs.cloud.google.com/apigee/docs/api-platform/system-administration/apigee-roles
- **Who grants what on the client side.** Who grants each kind of role:
  - Organization Administrator (`roles/resourcemanager.organizationAdmin`) or folder admins grant inherited roles.
  - Project IAM Admin (`roles/resourcemanager.projectIamAdmin`) and Security Admin (`roles/iam.securityAdmin`) grant roles on target resources, including to agent identities.
  - Billing Account Administrator handles billing links and Marketplace.
  - An Organization Policy Administrator sets constraints such as `vertexai.allowedModels`. This is the standard Org Policy role; the Agent Platform page does not name it.

  Source: https://docs.cloud.google.com/iam/docs/auth-agent-own-identity ; https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy ; https://docs.cloud.google.com/billing/docs/how-to/billing-access
- **Restricting which models can be used.** The org policy `vertexai.allowedModels` takes entries of the form `publishers/PUBLISHER/models/MODEL:ACTION`, where ACTION is `predict`, `deploy` or `tune`, for example `publishers/google/models/gemini-3.5-flash:predict`. There are no wildcards and at most 500 values. It can be set at organization, folder or project level, and an explicit deny overrides an allow. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/control-model-access
- **IAM Unified Access Policies (UAP, IAM v3 "Access policies") govern agent traffic through Agent Gateway.** Rules carry allow or deny effects, with deny overriding allow, on agent principals with CEL conditions such as tool name, HTTP method or path prefix. They are bound to the project that holds the gateway and enforced by IAP, in `DRY_RUN` (audit-only) or `ENFORCE` mode. Release notes give them as GA on 2026-08-31; the 2026-05-06 blog had said "coming soon". Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/iam-overview-uap ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes

## 4. Governance, security and compliance
- **Google's training restriction for Agent Platform.** "Google won't use your data to train or fine-tune any AI/ML models without your prior permission or instruction." It applies to GA and pre-GA managed models and is set out in the Service Specific Terms, with processing covered by the Cloud Data Processing Addendum. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance ; https://cloud.google.com/terms/service-terms
- **Data caching and how to switch it off.** Implicit caching for Gemini is on by default. In-memory and durable caches are project-scoped and deleted within 24 hours, and the durable cache does not support CMEK. A principal with `roles/aiplatform.admin` can turn off durable caching or all caching per project; organization-wide changes go through the account team. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance
- **Abuse monitoring and zero data retention.** Google may log prompts to detect Acceptable Use Policy abuse. Zero data retention requires all of the following:
  - request-response logging left off;
  - `store = false` on the Interactions API (the default is `true`);
  - caching disabled;
  - no Live API session resumption;
  - no Sandbox Snapshot API.

  Deep Research session data is kept for 7 days and cannot be disabled. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance
- **Grounding with Google Search retains queries.** Query logs are kept up to 3 days, with no opt-out. For zero data retention Google points to Web Grounding for Enterprise. Grounding with Google Search and Google Maps supports none of data residency, CMEK, VPC-SC or Access Transparency. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/security-controls
- **Gemini data residency.** Data at rest stays in the customer-selected location. ML processing depends on the endpoint:
  - `us`/`eu` multi-region endpoints (`aiplatform.eu.rep.googleapis.com`; EU excludes UK and Switzerland) keep processing inside that jurisdiction;
  - single-region endpoints keep processing inside the broader country or multi-region jurisdiction, varying by model;
  - the `global` endpoint gives "no regional isolation or data residency guarantees".

  Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/learn/data-residency ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/learn/locations
- **Blocking the global endpoint.** The org policy `constraints/gcp.restrictEndpointUsage` can block global endpoint requests. Multi-region `.rep.` endpoints do not support Private Google Access, so use Private Service Connect instead. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-partner-models ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/learn/locations
- **The Agent Platform security-controls matrix is per model.** GA Gemini models list data residency, CMEK, VPC-SC and Access Transparency for online and batch inference. Context caching lacks CMEK. "Security controls are not supported for preview models." RAG Engine supports CMEK and VPC-SC but not data residency or Access Transparency. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/security-controls
- **VPC Service Controls basics.** Service perimeters block API access across the boundary. Access Context Manager access levels, ingress and egress rules (preferred over bridges), and dry-run mode refine them. `restricted.googleapis.com` resolves to 199.36.153.4/30. An organization has one org-level access policy, and scoped policies delegate perimeter administration to folders or projects. Source: https://docs.cloud.google.com/vpc-service-controls/docs/overview
- **VPC-SC coverage for Agent Platform.** The perimeter covers Gemini generative AI, online and batch inference, tuning, Vector Search, Pipelines, Colab Enterprise, Agent Runtime and sandboxes. Limitations:
  - Agent Runtime agents deployed before the project joined the perimeter are not protected.
  - Agent Runtime has no internet egress, so it needs a proxy in an RFC 1918 subnet plus Cloud NAT.
  - Endpoints must be created after joining the perimeter.
  - URL-context live fetching and request-response logging are unavailable.

  Source: https://docs.cloud.google.com/vertex-ai/docs/general/vpc-service-controls
- **Recent VPC-SC changes for agents.** Agent Gateway enforces perimeter rules with `ALL_TRAFFIC` egress mode for deployments created after 2026-09-08. Computer Use and Shell sandboxes went GA with VPC-SC and Private Service Connect on 2026-09-09. VPC-SC support for Agent Identity ingress and egress rules was Preview per the 2026-05-06 blog. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes ; https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/
- **CMEK for Agent Platform.** CMEK covers Agent Runtime, sandboxes, endpoints, models, datasets, batch jobs, pipelines and Vector Search. The Agent Platform Service Agent needs `roles/cloudkms.cryptoKeyEncrypterDecrypter` on the key. The key must be in the same region as the resource, not dual- or multi-region, with one exception: serving profiles for the Gemini Live and Interactions APIs need `us`/`eu` keys. Source: https://docs.cloud.google.com/vertex-ai/docs/general/cmek
- **Recent CMEK additions.** CMEK for Gemini 3 tuning jobs and tuned models went GA on 2026-10-19. Memory Bank instances can choose Google-managed or Cloud KMS encryption in the console from 2026-11-06. Memory Bank and Sessions do not support the global endpoint for CMEK. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes ; https://docs.cloud.google.com/vertex-ai/docs/general/cmek
- **Agent Gateway is the enforcement point for agent traffic.** It governs client-to-agent (ingress) and agent-to-anywhere (egress) traffic for Agent Runtime and Gemini Enterprise agents, and is default-deny: "all connections are blocked unless an explicit IAM policy grants access". It integrates IAP, Unified Access Policies, Model Armor and Agent Registry (up to 5,000 registered resources per gateway). GKE and Cloud Run support is "coming soon". Cross-cloud support went to Limited Preview on 2026-11-11. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/gateways/agent-gateway-overview ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Model Armor is Google Cloud's AI guardrail service.** It screens prompts and responses for prompt injection and jailbreaks, sensitive data (via Sensitive Data Protection), malicious URLs (the first 256), RAI categories and CSAM. Floor settings enforce minimum protections across a project. It is billed on tokens screened. Source: https://docs.cloud.google.com/model-armor/overview
- **Model Armor integrations announced at Next '26.** Google announced inline Model Armor for Agent Gateway, Agent Runtime and Google Cloud MCP servers, with the Firebase integration GA (blog of 2026-05-06). Source: https://cloud.google.com/blog/products/identity-security/whats-new-in-iam-security-governance-and-runtime-defense/
- **Audit logging for Agent Platform.** Admin Activity logs for `aiplatform.googleapis.com` are always on. Data Access logs, which include `generateContent` and `predict` calls as "data read", are off by default and must be enabled. Reading them in `_Default` needs Private Logs Viewer. Source: https://docs.cloud.google.com/vertex-ai/docs/general/audit-logging
- **Agent Gateway and UAP violations are audit-logged.** In dry-run mode, disallowed agent communications are written to Cloud Audit Logs without being blocked. Inference request metadata logging went GA on 2026-10-30. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/policies/iam-overview-uap ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Data residency for Agent Runtime state.** Release notes of 2026-06-18 tie Memory Bank and Sessions residency to configuring the resource location constraint in organization policy (`gcp.resourceLocations`). (unverified: full wording truncated) Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Compliance attestations.** Generative AI on Vertex AI and Vertex AI Search received FedRAMP High authorization, announced 2025-03-20. Agent Search lists FedRAMP, ISO 27001, 27017, 27018 and 27701, SOC 1/2/3, PCI DSS, BSI C5:2020 and HIPAA (a BAA is required). Source: https://cloud.google.com/blog/topics/public-sector/vertex-ai-search-and-generative-ai-with-gemini-achieve-fedramp-high ; https://docs.cloud.google.com/generative-ai-app-builder/docs/compliance-security-controls

## 5. Commercial model
- **Gemini on Agent Platform is billed per token.** Pricing is per 1M input and output tokens, and varies by model and endpoint type (global, regional or multi-region). Google's pricing pages are https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing and https://cloud.google.com/products/gemini-enterprise-agent-platform/pricing; both rendered without readable rates on 2026-11-14, so no figures are quoted here. Source: https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-partner-models
- **Consumption options for Gemini on Agent Platform.**
  - Standard PayGo: the per-token standard rate. Tier 4 (above $50,000 per 30 days) was added 2026-09-10.
  - Priority PayGo: a per-token premium rate with a ramp limit.
  - Flex PayGo: about 50% cheaper, latency-tolerant.
  - Batch inference: 50% cheaper than Standard.
  - Provisioned Throughput: a fixed-term commitment.

  Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/deploy/consumption-options ; https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Provisioned Throughput is bought in GSUs.** GSUs (generative AI scale units) are purchased on 1-week (Google models only), 1-month, 3-month or 1-year terms. Fees can't be cancelled mid-term. Overage spills to Standard PayGo by default and can be controlled per request. Auto-renewal applies to monthly and longer terms. A 1-year term is priced 26% below the 1-month term. Ordering needs `roles/aiplatform.provisionedThroughputAdmin`. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/provisioned-throughput/purchase-provisioned-throughput ; https://docs.cloud.google.com/vertex-ai/generative-ai/docs/deploy/consumption-options
- **Recent Provisioned Throughput updates (release notes).** Throughput for newly GA models is quoted in tokens per second per GSU; for example, Gemini 4 Hydrogen went GA on 2026-11-12 at 685 tokens/sec per GSU. Provisioned Throughput for supervised fine-tuned models went GA on 2026-11-04. Gemini 4 Hydrogen cache writes are billed at 1.25x the input price from 2027-01-12. Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Agent Runtime and its add-ons are billed on compute and usage.**
  - Runtime: vCPU-hours and GiB-hours of memory.
  - Session and Memory Bank compute: metered on the Agent Platform compute SKU since 2026-09-01.
  - Memory Bank embedding SKUs: changing.

  Third-party summaries quote roughly $0.085 per vCPU-hour and $0.009 per GiB-hour under the 2026 SKU consolidation; Google's pricing page did not render to confirm. (secondary) Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes ; https://ecorpit.com/gemini-enterprise-agent-platform-cost-breakdown-2026/
- **Partner models are billed through Google Cloud.** Partner models from Model Garden, such as Claude, are enabled through the Cloud Commerce Consumer Procurement entitlement. They are billed pay-as-you-go per request, or through Provisioned Throughput ("contact sales"), with pricing that varies by endpoint type. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-partner-models
- **Agent Gateway cross-cloud is free during Limited Preview.** Products configured with it (Model Armor, Cloud Logging, Cloud Trace) are billed at standard rates (release note of 2026-11-11). Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes
- **Per-character billing is not in the current docs.** No current Agent Platform doc found in this research mentions per-character billing for current Gemini models; the docs describe per-token units. Source: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/deploy/consumption-options
- **Gemini Enterprise, Gemini API / AI Studio and Workspace are covered elsewhere.** These per-seat or separate-API products are in a separate note. Their Google Cloud IAM touchpoints are the Discovery Engine service agents (`@gcp-sa-discoveryengine`) and Agent Identity support for Gemini Enterprise agents. Source: https://docs.cloud.google.com/iam/docs/service-agents ; https://docs.cloud.google.com/iam/docs/agent-identity-overview
